# 星露谷農場手帳｜產品規格與完整化 Roadmap

更新基準：2026-08-13

本文件是手帳目前的正式產品規格與設計決策來源。GitHub Issues 用於追蹤執行狀態；若規格與 Issue 文字衝突，以本文件為準，並同步修正 Issue。

## 產品定位

這不是另一個 Stardew Valley Wiki。核心使用情境是：玩 Switch《星露谷物語》時，把手機放在旁邊，快速記錄目前存檔、查正在玩的內容，並主動提醒當下值得注意的事情。

完成版的判斷標準不是「資料是否百分之百齊全」，而是：**玩遊戲時約 95% 的臨時問題，可以直接在手帳解決，不需要另外開 Wiki。**

因此後續功能取捨以「是否改善實際遊玩流程」優先，不為了百科完整度無限補資料。

## 資訊架構總則

底部 6 個主導覽維持不增加，各頁責任固定：

- **總覽**：目前日期、存檔摘要與「今天可以做什麼」。
- **資料**：只放玩家這個存檔自己的記錄／進度，例如角色、農場、社區、收藏。
- **社交**：以 NPC 本人與玩家關係為中心，例如好感、生日、禮物、今日行程與人物服務。
- **查找**：放遊戲本身的客觀參考資料；一級只分 **世界／物品**，預設先進世界。
- **衣櫥**：角色、寵物與馬匹外觀／穿搭。
- **備註**：玩家自己的文字記錄與輔助內容。

核心區分：**資料＝我的遊戲現在是什麼狀態；查找＝遊戲世界本身有什麼、在哪裡、怎麼取得／使用；社交＝這個 NPC 是誰、我和他的關係以及今天去哪裡找他。**

## 0｜基礎整備（Issue #37）

### 0A｜語言、名稱與資料 ID

- App 自己的 UI、提示、說明、功能文案使用繁體中文／台灣用語。
- 遊戲內專有名詞以 **Switch 版《星露谷物語》遊戲本體實際顯示名稱**為準，不自行繁體化或另譯。
- 搜尋層支援繁中／簡中／英文 aliases，顯示名稱與搜尋別名分離。
- 新資料使用 stable ID，不用顯示文字直接作為資料 ID。
- CI 不能粗暴地「看到簡體字就 fail」；必須區分 App-owned 文案與合法的 Switch 遊戲名詞。

### 0B｜首次載入與資料拆分

- 非首頁必要的大型資料延後到進入功能時載入。
- 第一批拆分完整 lookup 與完整衣櫥目錄；後續世界、NPC 行程、完整分類沿用同一原則。
- 全站共用的 Switch 名稱映射不因某個頁面使用就誤當成單頁資料拆掉。
- 保持 Safari 15／iPhone PWA 相容。

### 0C｜降低 Wiki 圖片單點依賴

- 底部導覽、主要功能 icon、NPC／日曆頭像、核心頁籤、日曆／地圖等高頻資產優先自架。
- 低頻圖片可保留 Wiki fallback＋Service Worker runtime cache。
- Wiki 暫時失效時，主要 UI 不能跟著大面積破圖。

### 0D｜衣櫥空白狀態

- 新手帳未選服裝時，預覽人物使用中性預設穿著。
- fallback 只用於畫面，不寫入使用者 wardrobe 存檔。
- 「我的搭配」仍顯示實際未選狀態。

### 0E｜Build／資料清理

- 清除 duplicate object key 與其他可控制的 build warning。
- 清理明顯重複、純數字、內部或錯誤 lookup 資料。
- 保留 Safari 15 esbuild、ESLint no-undef、sw.js 語法與 renderer/static audit。

### 0F｜存檔 schemaVersion

- 正式存檔加入頂層 `schemaVersion`。
- 新存檔使用目前 schema；既有無版本存檔辨識為 legacy，而不是直接假裝成最新格式。
- localStorage、Supabase、唯讀分享、JSON 匯入／匯出都保留版本欄位。
- 真正的進度資料 migration 留給第 1 項進度聯動實作。

### 0G｜自動產生資料可重現性

- generator 與 pinned source 若存在，應跟資料一起留在 repo。
- generator 目前缺失的資料檔視為 committed snapshot，清楚記錄來源狀態；不得用不明腳本重新覆寫正式資料。
- 後續恢復 generator 時，要先證明重建結果可重現且不會洗掉人工修正。

0 項內部順序：`0A 邊界／ID 規則 → 0E 清理 → 0F schemaVersion → 0G 生成資料來源 → 0B 載入拆分 → 0C 核心圖本地化`；0D 可獨立併行。

## 1｜遊戲事實／進度聯動

目的：同一件遊戲事情不要讓玩家在多個地方重複記錄。

聯動不是無條件雙向推論。只有語意足夠明確的完成事件可以推導其他結果：

- 食品儲藏室完成 → 溫室已解鎖。
- Joja 溫室工程完成 → 溫室已解鎖。
- 礦井 120 層 → 頭骨鑰匙取得。
- 保險庫完成 → 巴士／沙漠解鎖。

局部狀態不能反推歷史過程，例如只在農場頁勾「溫室已建」，不能自動假設社區中心收集包已繳。若在「里程碑：溫室已解鎖」這種語意明確入口完成，則可依目前路線同步社區中心整室或 Joja 工程；路線未知時先要求選路線，不猜。

社區中心上方「整室完成：XXX」小卡本身可直接標記完成，移除頁尾重複入口；取消整室完成時保留玩家逐項勾過的收集包資料。

## 2｜總覽「今天可以做什麼」

這是完整化功能的核心之一。目標不是每天指揮玩家怎麼玩，而是告訴玩家今天／本季有哪些值得注意、容易錯過，或現在剛好可以推進的事情。

首頁約放 3–6 個高價值提示，優先順序：

1. 今天錯過就沒了：生日、節日、天氣限定魚、今日限定事件、作物最後播種日。
2. 本季值得處理：本季未收集魚、社區中心目前季節可取得缺口、季末快錯過內容。
3. 現在可以推進：只有理由明確時顯示，例如某解鎖只差最後一步。

不要無理由出現「今天建議下礦／升工具／做設備」這類泛攻略建議。

每張提示要回答：**為什麼現在顯示？要做什麼？點下去去哪裡？** 卡片優先原地展開細節，需要完整功能頁時才使用次要跳轉。

### 天氣

天氣不是必填。未記錄天氣時，同時顯示「☀️ 如果晴天」與「🌧️ 如果下雨」等分支；日期、季節等已知條件照常計算，不因沒填天氣而把限定內容藏掉。若玩家記錄實際天氣，才只顯示符合該天氣的一套結果。

可提供輕量狀態：`未記錄｜☀️｜🌧️｜⛈️｜🌿｜❄️`。

## 3｜查找 → 世界

### 一級架構

「查找」一級只保留 **世界／物品**，預設先進世界。「找魚」不是第三個一級頁籤；魚屬於世界的空間關係，正常瀏覽應沿著地圖往下找。

### 世界主流程

世界正式採 **Map-first（地圖優先）、由大到小**：

`大世界地圖 → 區域 → 區域地圖 → 地點／釣點 → 具體資料`

例如：

`本島大世界地圖 → 煤矿森林 → 煤矿森林區域地圖`

進入區域後只分兩種主要內容：

#### 地點

地點包含商店、建築、設施與特殊地點，例如玛妮的牧场、法师塔、旅行货车、莉亚的农舍、秘密森林。

點地點後原地展開：營業時間、解鎖／使用條件、可以做什麼、商品／服務、相關 NPC 與相關入口。

**人物不與「地點／釣點」並列成區域的一級分類。** 世界中的人物是地點關聯；點 NPC 後可進「社交 → NPC」。反向也成立：社交的今日行程點地點，可回到世界對應位置。

世界負責「人在哪裡／和哪個地方有關」；社交負責「這個人是誰／關係／禮物／完整行程」。

#### 釣點

釣魚納入同一套空間階層，不再跳往平行的獨立找魚頁：

`世界 → 區域 → 釣點 → 水域 → 魚`

區域的釣點模式使用區域範圍地圖，標示河流、池塘、瀑布、湖泊、特殊水域等。點某個釣點後，在目前世界頁顯示該處魚類，再用季節／天氣／時間等條件篩選。

既有找魚的點地圖互動與 fish data 繼續重用，但成為世界系統的一部分，不另外複製一套魚資料。

同一水域若可從「地點」與「釣點」兩條路徑到達，最後必須指向同一個 fishing spot stable ID。例如「秘密森林」地點內的可釣魚入口，與「煤矿森林 → 釣點 → 秘密森林水池」應共用同一實體。

### 地圖層級

第一層先選本島、姜岛或特殊區域；本島與姜岛使用遊戲地圖。

第二層從大世界地圖點區域，例如鹈鹕镇、煤矿森林、山區、海滩等，再進入該區自己的地圖。

第三層區域地圖依模式切換標記：

- **地點模式**：商店／建築／設施／特殊地點。
- **釣點模式**：河流／湖／池塘／瀑布／其他水域。

區域頁不要做成 `地点 5｜人物 3｜找鱼` 這種統計 dashboard；地圖本身才是主要導航。

### 快速反查

正常流程是從地圖由大到小，但世界另保留兩個輕量反向查找工具：

- **🎣 按條件找魚**：適合只知道季節／日期／天氣／時間，不知道去哪裡。結果以「魚 → 區域 → 具體釣點」呈現，點結果定位回世界對應釣點，不開另一套頁面。
- **👤 按條件找人**：回答「今天／現在 NPC 在哪裡？」。條件可使用年份、季節、日期／星期、天氣、遊戲時間、區域與 NPC 名稱。結果可「點位置 → 世界」或「點人物 → 社交」。此能力依賴第 5 項 NPC 今日行程資料；行程資料未完成前，不另造一套不可靠的簡化資料。

### 世界資料邊界

世界**資料層**重要，但瀏覽頁不做成大型 Wiki。主要回答：**我在哪裡？我要去哪裡？這裡有什麼？這裡能做什麼？哪裡可以找到這個人／這條魚？**

不補大量背景故事或長篇攻略；人物詳細資料回社交，物品詳細資料回物品。

區域、地點、釣點、NPC、物品都使用 stable ID；正式顯示遵守 Switch canonical name；搜尋另保存繁中／簡中／英文 aliases。既有資料可重用就重用，不建立第二份商店、人物或魚類資料庫。世界資料維持 lazy load。

## 4｜全域搜尋

與「今天可以做什麼」同屬最高價值功能。目標是腦中想到一個詞就直接搜，不需要先知道它屬於哪個頁面。

搜尋實體包含人物、物品、地點、建築、功能、收藏／進度、社區中心／Joja、魚類釣點等。

例如：

- 搜「羅賓」→ NPC、木匠店、建築服務、今日行程。
- 搜「溫室」→ 農場建築、里程碑、食品儲藏室、Joja 工程、目前解鎖狀態。
- 搜「熔岩鰻魚」→ 物品、釣點、魚塘、收藏、送禮等相關資料。

搜尋支援 Switch canonical name、繁中 alias、簡中 alias、English alias 與模糊搜尋，並沿用跨頁返回與原位置恢復。

## 5｜NPC 今日行程

第一版做薄版，整合既有社交速查，不建立第二套 NPC 百科。

人物卡優先回答「今天去哪裡找他？」；若知道目前遊戲時間，可高亮目前應在的位置，否則顯示當日時間軸。系統依季節、星期、天氣、特殊條件挑選今天正確的行程；完整全年／特殊行程藏在「展開全部」。

這份行程資料同時是「世界 → 👤 按條件找人」的唯一資料來源：世界負責位置反查，社交負責人物本身，不維護兩套行程。

## 6｜種植計算器

**不做售價、不做收益、不做星級、不做職業價格加成。** 手帳的實際需求是日期，不是收益精算。

第一版輸入：目前日期（自動帶入）、作物、種植地點（農場戶外／溫室／姜島）、真正影響生長速度的條件（生長肥料、農業學家等）。

輸出：成熟日期、現在種是否來得及、本季還能收幾次、最後播種日、多次收成作物的後續收成日期。

結果可供「今天可以做什麼」使用，例如最後播種日提醒。

---

## 7｜查找分類補齊

不追求所有資料都有完美分類，只補「不知道名字、想用類型瀏覽」的實際情境。

已有魚、料理、製作、設備、博物館、收集包、出貨等分類繼續保留；優先新增／改善家具／裝飾、農作物、種子、採集、畜產品、武器／裝備等真正有查找價值的類別。

其中家具／裝飾是確定需求，但不為了分類率 100% 維護大量冷門／內部分類。

---

## 8｜常用／關注 ⭐

NPC、物品、地點、建築可加星號。總覽提供精簡「正在追／常用」區，不另做龐大「我的」頁。

關注資料可供「今天可以做什麼」提高提示優先級：正在追的東西今天剛好能取得時，優先顯示。

## 價值排序

`今天可以做什麼 ≈ 全域搜尋 > 進度聯動 > 關注／常用 > 世界資料層 > NPC 今日行程 > 種植日期計算 > 查找分類補齊`

這不是實際開發順序，因為存在資料依賴。

## 完成後定位

完成上述完整化後，手帳應具備：存檔進度管理、收藏圖鑑、人物速查、世界資料、今日遊玩提醒、全域搜尋、種植日期工具、跨頁／跨資料聯動與常用追蹤。

之後主要進入資料準確度、實機 UX、效能、穩定性與小型便利改善，而不是持續無限制增加大型百科頁面。
